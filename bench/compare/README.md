# Competitor comparison

Runs the same tasks through CDPEx, [playwright_ex](https://hex.pm/packages/playwright_ex),
[ChromicPDF](https://hex.pm/packages/chromic_pdf) and [Wallaby](https://hex.pm/packages/wallaby),
on the same pages and the same Chromium, and probes every capability in the
README's comparison table by running code, not by reading docs. Not part of the
Hex package; a separate mix project, so CDPEx's own dependencies don't change.

```bash
bench/compare/run.sh                                  # probes + 3 rounds of every task
ROUNDS=0 bench/compare/run.sh                         # probes only
PROBE=0 ROUNDS=1 TASKS="screenshot:js" LIBS="cdp_ex wallaby" bench/compare/run.sh
```

Results land in `bench/results/compare-<timestamp>/` (ignored by git):
`report.md` (both tables), `results.jsonl` (one line per run),
`capabilities-<lib>.json`, `env.txt` (versions), and each run's stdout and stderr.

## Setup

- **One image, one browser** (`Dockerfile`): Debian trixie's `chromium` and
  `chromium-driver` (always the same version), Elixir 1.20.5 / OTP 27, and the
  Playwright driver (`playwright-core`, only its `run-driver`; no bundled
  browsers). Every library is pointed at `/usr/bin/chromium`. Native on arm64
  and amd64; Google publishes no linux-arm64 ChromeDriver, hence Debian's pair.
- **A fresh container per run.** Every (task, page, library) runs in its own
  `docker run --rm`, capped to `CPUS` CPUs, so whatever a library starts (the
  Node driver, ChromeDriver, Chrome) dies with it. Before and after every run
  the script checks that no run container is left and stops if one is. Library
  order rotates between rounds.
- **The fixture runs in its own container** (`fixture/server.mjs`), reachable as
  `site.test` and `embed.test`: two sites for Chrome, so the `heavy` page's
  embed is a real cross-site, out-of-process iframe. Every response waits
  `DELAY_MS` (20). It also runs a forward proxy with a login (port 3128) and
  logs requests, for the block and proxy probes.
- **Viewport 1280×800 for all**; the screenshot probe fails on any other PNG
  size. Each library gets there its own way: CDPEx `set_viewport/3` per page,
  playwright_ex the context's `viewport`, ChromicPDF and Wallaby a window
  143 px taller than the viewport (headless Chrome's frame).

## Pages

| Page | What | Ready when |

## Tasks

Every library gets every task; one that it can't do shows "can't" with the
reason. A job always opens the page itself.

| Task | One sample |
|------|------------|
| `screenshot` | open → ready → PNG of the viewport |
| `pdf` | open → ready → PDF |
| `text` | open → ready → read a known element's text |
| `click` | open `js` → ready → click the first article → wait for its page → read its heading |
| `cold` | start the library and its browser → `screenshot` of `html` → stop everything |
| `concurrent` | `CONCURRENCY` (8) workers doing `screenshot` of `html` back to back for `DURATION_S` (20) s |

How each library runs its jobs, the way its docs show:

| Library | Sequential tasks | `concurrent` |
|---------|------------------|--------------|
| CDPEx | one browser, `new_page(isolated: true)` per job (a fresh context, as `Pool.with_page/3` does) | the same, 8 workers on one browser |
| CDPEx (reuse) | one page, opened at start and navigated by every job | a page per worker on one browser |
| CDPEx (pool) | – | `CDPEx.Pool` of 8 browsers, `Pool.with_page/3` |
| playwright_ex | one browser, a new context + page per job | the same, 8 workers |
| ChromicPDF | `capture_screenshot` / `print_to_pdf` on its session pool | session pool of 8 tabs in one Chrome |
| Wallaby | one session, reused | 8 sessions (one Chrome each) |

"cdp_ex" and playwright_ex pay for a new context and page per job; ChromicPDF,
Wallaby and "cdp_ex (reuse)" navigate a tab that already exists. Compare like
with like. The `js` page's waits and targets each match one element
(`.article-preview:first-child`): Wallaby checks the visibility of every element a
query matches, and on the 20-item list that alone cost about a second per job.

Workarounds that show up in the timings are marked ¹ in the report: ChromicPDF
can't wait for an element to appear (`:wait_for` needs it to exist), so on
`js` it awaits an `:evaluate` Promise that polls for it; playwright_ex has no
PDF function, so `pdf` sends the raw protocol message. Wallaby's documented
`take_screenshot/2` writes the PNG to disk, which its numbers include.

## Columns

- **p50 / p95 ms** of one run's samples; **jobs/s** for `concurrent`.
- **PSS peak MB**: the largest sum of PSS over the run's processes, sampled every
  `INTERVAL_MS` (100) from `/proc`, split into browser / driver (Node,
  ChromeDriver) / BEAM. This is the memory figure to compare.
- **memory peak MB**: the container cgroup's `memory.peak`. It undercounts shared
  files (Chromium's binary is charged to whichever container read it first),
  so it reads lower than PSS.
- **CPU s**: the cgroup's CPU time over the timed part.

Each figure is the median over rounds.

## Probes

`Compare.Probe` runs every capability for every library (35 rows). Each result
is checked, not just called (a PNG of the right size, a PDF, PDF/A metadata,
the expected text, a request log showing nothing was fetched):

- **✓** done through the library's API, result checked;
- **partial** done only by a workaround, which the note names;
- **✗** no way in the public API; the note says what was looked for;
- **fail** the API exists, the check failed; **error** the probe crashed.

Firefox and WebKit are probed in a separate image (`Dockerfile.browsers`, with
Playwright's own builds) and, for Wallaby, against a pinned
`selenium/standalone-firefox` container; they are never timed.

What the numbers say, read with the setup table above in mind:

- **A new context per job costs ~80–200 ms.** "cdp_ex" (a fresh context per
  job) against "cdp_ex (reuse)": 266 vs 155 ms for a `js` screenshot, 546 vs
  351 on `html`. playwright_ex pays the same: it is within 10% of "cdp_ex" on
  every sequential task but two, `click` (343 vs 233 ms) and the `html` PDF,
  where it is faster (1485 vs 1850 ms).
- **Reusing a tab**, "cdp_ex (reuse)" is the fastest row on every task but the
  `html` PDF (1542 ms, behind playwright_ex's 1485): ahead of ChromicPDF on
  screenshots and PDFs (`js` screenshot 155 vs 204 ms), of Wallaby on
  interaction (`click` 130 vs 639 ms), and at 6.0 jobs/s in `concurrent`
  against ChromicPDF's 5.0.
- **ChromicPDF**, whose session pool reuses tabs too, is the fastest library
  default for screenshots and PDFs of `js` and `heavy`; Wallaby is faster on
  the `html` screenshot (399 vs 438 ms). It reads nothing back from a page, so
  `text` and `click` are out of its reach.
- **playwright_ex** prints the long `html` page fastest, through the raw
  protocol, and carries ~140 MB for the Node driver.
- **Wallaby** is slowest at interaction (each step is a WebDriver round trip)
  and, with a Chrome per session, needs the most memory under load (3.3 GB PSS
  for 8 workers vs 1.4–1.8 GB on one browser).
- **Cold start**: CDPEx 833 ms, ChromicPDF 981, playwright_ex 1353 (the Node
  driver starts too), Wallaby 1431 (ChromeDriver too).
- A reused tab keeps more memory between jobs: "cdp_ex (reuse)" and Wallaby
  peak at ~1 GB PSS on the `html` page against ~650 MB for a fresh page per job.
